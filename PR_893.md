## Summary

`projectProposalCreated()` updated the proposal row, deleted the previous action set and then saved each decoded action in its own write. A decoding or persistence failure in the middle of that loop left a committed proposal with an empty/partial action set, which a retry could never repair and the read API could expose.

This PR makes a `ProposalCreated` projection a single atomic unit:

- All calls are decoded and validated **before** any committed row is changed. Mismatched `targets/values/calldatas` arrays are rejected without writing.
- Proposal upsert, action-set replacement and projection provenance are committed in one `TransactionRunner.run()` transaction. A failure rolls everything back, preserving the last committed read model.
- The same row lock is taken inside the transaction and the fully-applied marker is re-checked there, so concurrent attempts cannot interleave action replacement and duplicate delivery stays idempotent.
- A dedicated `createdEventTxHash` / `createdEventLogIndex` / `actionCount` projection identity is stored on the proposal row (with an idempotent migration). Unlike `lastEvent*`, it is not overwritten by later lifecycle events, so a retry can tell whether the exact `ProposalCreated` event was fully applied — including repairs of mixed state left by older non-atomic projectors.
- `GovernanceReadService.getProposal()` now reads proposal, actions and vote totals inside one `REPEATABLE READ` snapshot, so clients only observe complete committed projections.
- Reorg replay uses the same atomic projector (`force` replay), restoring the exact canonical action set.

### Persistence architecture (#831)

No new ORM, `DataSource` or competing persistence authority is introduced. The change reuses the repository's existing TypeORM boundary through the repository's shared `TransactionRunner` helper (V2-BE-111 / `ARCHITECTURE.md`). The `GovernanceV2Module` imports the existing `DatabaseModule` explicitly so the shared runner is available where the module is wired.

### Tests

New/updated cases in `governance-projection.service.spec.ts` and `governance-read.service.spec.ts`:

- decoding failure leaves the prior proposal/action projection unchanged
- save failure rolls back the proposal update and all action changes
- successful projection replaces the full action set atomically (single bulk write inside one transaction)
- replay of the same canonical event produces no duplicate or partial action rows
- later state transitions do not invalidate `ProposalCreated` idempotency
- a legacy partially applied projection is repaired atomically
- concurrent projection attempts cannot interleave action replacement
- read API never observes a partially replaced action set committed mid-request
- reorg rollback followed by replay restores the exact canonical action set
