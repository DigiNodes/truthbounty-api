## Summary

`TokenService.issueCapabilityToken()` read the undeclared `options.ttdSeconds` property instead of the declared `options.ttlSeconds`, so a caller-supplied TTL was ignored and the hard-coded maximum was always used. This PR makes the declared option authoritative and hardens issuance so no token can be returned without a persisted replay nonce.

Closes #845

## Changes

- `src/auth/services/token.service.ts`
  - Read only `options.ttlSeconds`; removed the `ttdSeconds` misspelling (also removes the `TS2339` undeclared-property error).
  - Added a single `resolveCapabilityTtl()` helper producing one validated effective TTL:
    - omitted → `CAPABILITY_MAX_TTL_SECONDS` (300s);
    - `NaN`, `Infinity`, `-Infinity`, `0`, negative and non-number values → `UnauthorizedException` (fail closed, logged as `[invalid-ttl]`);
    - otherwise → floored to whole seconds, minimum 1, capped at the hard maximum.
  - The same `ttlSeconds` value is now used for JWT `expiresIn`, the Redis nonce record TTL, response `expiresIn` and audit metadata (`ttlSeconds` key).
  - The replay nonce is persisted **before** signing; if `RedisService.set()` reports failure, issuance throws `UnauthorizedException` (`[nonce-persist]`) and no token is returned.
  - Documented the TTL contract on `IssueCapabilityOptions.ttlSeconds`.
- `src/auth/services/token.service.capability.spec.ts` (new): 16 boundary tests — omitted, minimum, sub-second, maximum, just-above-maximum, day-long clamp, fractional flooring, zero/negative/NaN/±Infinity/non-number rejection, ignored `ttdSeconds`, `ttlSeconds` precedence, and fail-closed nonce persistence.
