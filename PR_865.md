## PREWAVE-BE-162 — Make legacy dispute outcomes projections of finalized contract events

### Problem

`DisputeService` created and transitioned disputes directly from HTTP request
data. Callers could supply `initiatorId`, `trigger`, `originalConfidence`,
`outcome`, `finalConfidence`, a rejection reason and terminal status. Those
local TypeORM writes had no canonical log identity, chain/deployment binding,
release artifact or finalized checkpoint, so a locally recorded outcome could
be mistaken for protocol dispute truth and diverge from the contract.

### Fix

- **No HTTP authority over outcomes.** `resolveDispute()` / `rejectDispute()`
  were replaced by `recordTriage()`: the deprecated `PATCH /:id/resolve` and
  `PATCH /:id/reject` routes now only append `metadata.reviewTriage` entries.
  They never write terminal `status`, `outcome`, `finalConfidence` or
  `resolvedAt`. The only terminal write path is the new
  `POST /disputes/:id/project-outcome` (moderator/admin), which accepts just a
  canonical log pointer.
- **Fail-closed evidence gate** (`DisputeEvidenceService`) resolves a
  `(chainId, txHash, logIndex)` pointer and re-derives every protocol field
  from a canonical `DisputeRaised` / `DisputeResolved` / `DisputeExpired` log.
  It rejects wrong chain, missing/reorged logs, unexpected event names,
  unapproved deployments, artifact drift, unsupported event schema,
  pre-deployment events, missing/invalid finalized checkpoints, challenger
  mismatch and claim/round mismatch with stable error codes.
- **Verified principal only.** `create()` takes the initiator from
  `request.user.address`; client-supplied identity fields were removed from
  the DTO. Trigger/confidence come from the canonical raise payload (otherwise
  `MANUAL` / `0`) and are never trusted from the request body.
- **Exact provenance & identity.** Rows carry `chainId`, `deploymentAddress`,
  `artifactVersion` (release), `eventTxHash`, `eventLogIndex`,
  `eventBlockNumber`, `canonicalClaimId` and `originalRoundId`, with a unique
  partial index on the canonical event identity. Duplicate/replayed logs are
  deterministic.
- **Explicit labelling.** `recordKind` (`LEGACY_WORKFLOW` /
  `CANONICAL_PROJECTION`) and `dataState` (`LOCAL_WORKFLOW` / `FINALIZED`)
  keep workflow metadata distinguishable from protocol outcome fields in API
  responses. `GET /disputes/expired` is now an attention queue, not an expiry
  authority.
- **Reorg/replay.** `reconcileReorg()` clears terminal projections above the
  new canonical head and demotes disputes whose raising event was reorged;
  `replayProjection()` rebuilds deterministically from canonical history and
  clears terminal state when no finalized terminal event remains.
- Migration `1793300000000-DisputeCanonicalOutcomes` adds the columns, labels
  all legacy rows non-authoritative, archives historical local outcomes in
  metadata and clears the authoritative columns. Docs:
  `docs/DISPUTE_CANONICAL_OUTCOMES.md`.

Coverage includes: client cannot inject another initiator or terminal
outcome/confidence; moderator triage cannot resolve/reject/expire a dispute;
finalized events project exact provenance; wrong-chain, wrong-deployment,
unfinalized, duplicate and reorged events are handled deterministically;
replay reproduces the projection; workflow and protocol fields are labelled
separately.
